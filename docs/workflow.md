# 从可玩布局到自然场景

本项目把 2D RPG 地图制作分为物理、渲染和内容三个独立阶段。先证明角色能走、门能进、出口相通，再让美术覆盖已确认的布局。AI 图片不能成为物理地图的隐式编辑器。

SDK `0.3.0` 负责确定性地图生成、碰撞与路径验证，以及渲染数据规划。Skill 负责指导 agent 组织制作、素材验收和引擎集成。公开包不包含用户录音、游戏截图、视频、字体或生成图片，不调用某个 AI 厂商，也不承诺一键完成整款 RPG。

## 1. 把需求变成可验证约束

在调用图像模型前记录以下信息：地图类型、尺寸、种子、角色碰撞半径、出口方向、建筑数量、必须到达的交互点、室内模板、相机视角、美术比例、素材来源和生成预算。

物理约束优先于装饰偏好。例如四出口城镇需要四条通向边界的主路；旅店的前台、房间和楼梯需要合法接近点；巨大的树冠可以覆盖路面，但树根不能堵门。不是所有美术像素都应参与碰撞。

```sh
npm install
npm run generate -- --layout symmetric --width 49 --height 49 --walls --out output/city.json
npm run generate -- --kind interior --template inn --symmetry quadrilateral --out output/inn.json
npm run examples
npm test
npm run check:types
npm run demo
```

`npm run sdk:pack` 产生可安装的本地包。仓库公开不等于已发布到 npm，不能把远程 `npm install @mossbrook/map-sdk` 当作已经存在的渠道。

## 2. Blockout：先布路，再放占地

用色块和简单几何体区分草地、道路、水、桥、墙和室内地板。为建筑记录根部占地、入口、门前接近格和未来图片范围；图片范围可以大于占地。

最大矩形算法回答的是“这一张布尔栅格上，哪一个由合法格中心组成的矩形最大”。它可用于观察广场容量、候选空地和布局密度，但不是通用房屋打包求解器。实际摆放还需要候选地块筛选、占地排斥、门前净空、保护道路和数量约束。最大矩形覆盖的格中心之间，也可能存在细围栏等连续障碍。

散村、对称城镇和规则街区不应该共用一种撒点策略。

| 方案 | SDK 当前实现 | 应用判断 |
| --- | --- | --- |
| `organic` | 固定 `48x36`，五栋房屋，河流与桥，四边出口 | 小村落、起伏自然的路径；不是任意尺寸散村求解器 |
| `symmetric` | 奇数尺寸 `25..129`，中心广场和四向主路 | 正方形保持 D4 旋转/镜像；长方形保持 X/Y 镜像 |
| `grid` | 尺寸 `25..129`，允许偶数，规则街区 | 更适合功能清晰、反复导航的城镇 |

结构化道路宽度支持 `3/5/7`。显式对称建筑数必须是 4 的倍数，而且要放得下；放不下应返回错误，不能悄悄减少数量。城墙方案只有四处主路开口。对称保证的是地形、占地和入口，不要求有透视的屋顶图片也能旋转对称。

## 3. 路径验证：节点可走不等于边可走

区分三个坐标域：整数格 `(x,y)`、连续地图中心 `(x+0.5,y+0.5)`、渲染像素。网格以 `[y][x]` 存储。默认圆形角色半径是 `0.28` 格；接入引擎后必须确认实际人物使用相同半径或按真实半径重新验证。

验证顺序：

1. 从实际碰撞体重建合法格中心。
2. 使用 BFS 计算连通区域，要求所有可行走格处于一个连通分量。
3. 对出生点到地标、出口、门口和家具接近点运行 A*。
4. 检查圆形角色沿每一条路径边的整个扫掠过程，而不只检查两端。
5. 检查物理地图与导航掩码一致，以及保护道路没有被新增实体覆盖。

SDK 当前使用四方向路径。格间细墙会阻断圆形角色移动；不应让 A* 忽略这类实体。游戏若额外实现任意角度移动、滑墙或动态 NPC 阻挡，需要引擎自己的实时碰撞测试，不能仅靠离线生成报告证明。

```js
import { createMapSDK, findPath, rebuildNavigation, assertValidMap } from "@mossbrook/map-sdk";

const sdk = createMapSDK({ seed: "tutorial-01" });
const map = sdk.generateTown({ layout: "grid", width: 49, height: 41 });
const route = findPath(map, map.spawn, map.exits[0]);
console.log(route.length, map.report.passed);

// 只有物理几何被外部编辑后，才需要重建导航。
rebuildNavigation(map);
assertValidMap(map);
```

将种子、参数、地图 JSON 和真实验证报告一起保存。不要把美术改动导致的路径错误隐藏在截图后面。

## 4. 室内模板先于 WFC

住宅、旅店、工坊需要不同的房间组织，不是把同一套隔墙换个名字。SDK 提供三个模板，并支持 `none`、`bilateral` 和 `quadrilateral` 对称。

| 模板 | 默认尺寸 | 最小尺寸 |
| --- | --- | --- |
| `cottage` | `17x15` | `15x15` |
| `inn` | `23x19` | `21x19` |
| `workshop` | `21x17` | `17x15` |

室内尺寸上限是 `101x101`。通道宽度是至少 3 的奇数，通道更宽时可能需要更大空间。家具密度在 `0..1`，摆放必须保留功能区的可达接近点。对称模式要求奇数尺寸和相应对称的显式门口。门的 `offset` 是边界整数格坐标，不是百分比。

`generateBuildingInterior` 派生稳定种子，并返回室内外 `connections`。引擎仍负责切场景、剧情、存档和传送表现。读取外部建筑的 `doors[]`，不能只读兼容的单个 `door`。

WFC 是可选扩展，**当前 SDK 没有实现 WFC**。它适合补充局部墙面、地板、家具组合；普通局部邻接约束不能自动保证整张图连通。接入时先锁定门户与主通道，再求解局部图案，按真实几何重建导航并运行同一个验证器。只允许有限重试；失败保留模板版本，不把不可达结果交给美术阶段。

## 5. 地面不是每格随机贴一张草

```js
import { createArtPlan } from "@mossbrook/map-sdk";
const plan = createArtPlan(map, { preset: "generic", tileSize: 32 });
```

`createArtPlan` 输出 `materials`、`transitions`、启发式场、`protected`、语义区、分组、贴花、接触阴影和纯渲染装饰。它不绘图、不调用 AI、不创建图集，也不修改碰撞。当前计划版本是 `1.0`，与 SDK 的 `0.3.0` 不是同一个版本号。

`transitions` 是 47 型 Blob 的邻接掩码：N/NE/E/SE/S/SW/W/NW 对应 `1/2/4/8/16/32/64/128`，对角位必须有相邻两个正交位。它不是已经做好了 47 张地砖。调用方要提供匹配图集、掩码到素材的映射或边界绘制器。

距离场采用多源曼哈顿 BFS；湿度、阴影、通行热度在 `0..1`，是混合纹理的启发式数据，不是水文或物理光照。路面高通行区域增加磨损，树根附近增加裸土与落叶，水边增加湿润与苔藓，建筑根部增加基础污迹，比独立均匀随机纹理更有关系。

地面可以选择两条路径：

- **算法贴图**：使用材质遮罩、47-Blob 边界规则、连续噪声、启发式场和稀疏贴花，在引擎中拼接。连续噪声和图集需由适配器提供，不是 SDK 已有的图片服务。
- **受约束 AI 底图**：把 blockout、材质区域、固定视角、固定边界和保护区提供给图像工具，只生成地面纹理。不能在底图中私增树干、墙、深水、房屋、门或台阶。提示词不是硬约束，生成后还要叠图验收。

大型地图可以分块，但必须统一像素密度、投影、边界参考和接缝验收。先保留可用的程序底图，AI 工具不可用时仍可生成和验证地图。

## 6. 物品摆放：语义分组，而不是均匀散点

自然环境先定义“院落、池岸、林缘、作业点”等语义区，再采样簇锚点和簇内成员。泊松盘负责最小间距，不负责故事、美术构图或可达性。树、竹、石、草分别使用不同间距与密度，簇内和簇间尺度也应不同。

先排除出生点、主路、门前与交互路线保护区，再对候选根部占地做检查。树冠图片可以重叠，树根与新增实体碰撞不能借此放宽。矮草贴花可以靠近路边，大树根和石块要离路更远。已有建筑、老树或水边可成为组锚点，物品有共同来源，而不是每件都孤立放在空地。

范围说明很重要：当前 `generic` 和 `plain` 提供基础规划与适用细节，不自动生成完整园林；两者也不等于关闭所有贴花。当前成簇林缘/池塘扩展属于 `fangcun` 预设，且仅对 `sceneId === "courtyard"` 生效，配景位置针对原始 `60x36` 庭院编写。给任意地图加上这个 ID 并不能自动泛化。公开包保留其逻辑接口，不附带特定场景素材。要支持任意新地图，需要外部语义摆放适配器，不能把专用示例宣传成通用自动美术。

## 7. 五层渲染与遮挡

1. 地表底图。
2. 地面贴花与接触阴影。
3. 按世界脚点深度排序的实体，包括建筑、树根、角色和物件。
4. 需要独立控制的屋檐/树冠前景，按人物相对位置决定遮挡或透明化。
5. 特效与单独管理的界面。

“前景层”不是把所有树冠永远盖在玩家上面。玩家走到树前应挡住对应实体；走到树后可以被树冠遮住，必要时局部透明。碰撞体、图片范围、脚点排序和遮挡范围是四个不同概念。

素材和动作序列的详细约定见 [asset-contract.md](asset-contract.md)。

## 8. Agent 协调和有限优化

| 角色 | 产出 | 不应越界 |
| --- | --- | --- |
| 布局与寻路 agent | 地图 JSON、门口与碰撞、验证报告 | 不因美术好看而绕过验证 |
| 美术规划 agent | 底图/独立实体任务、分组规则、图层计划 | 不私改门、路和碰撞 |
| 素材 agent | 候选图片、锚点/帧清单、来源记录 | 不把失败图当成已验收图 |
| 集成 agent | 引擎映射、锚点投影、排序与动画 | 不把 sprite 包围盒当统一碰撞体 |
| QA agent | 实际路径/遮挡/画面证据、失败原因 | 不凭感觉宣布所有检查通过 |

所有角色共享一个版本化合同。移交至少包含 `contractVersion`、地图 ID/种子、变更文件、碰撞是否改变、实际检查结果、未解决问题、素材来源。布局版本改变后，引用旧遮罩的图片任务必须标记过期。

建议初始预算：每种素材最多 3 个候选，布局最多 2 次重生成。不是固定法规，可随项目调节。只重做失败槽位；失败写明是锚点、尺寸、轮廓、禁区还是动作相位不满足。预算耗尽保留已验证 blockout/占位素材并报告，不无限重试，不自动更换付费服务。

## 9. 可复现验收

- 相同种子和参数输出相同地图；修改美术种子不修改物理地图。
- 四个出口、所有地标、所有门口和家具接近点实际可达。
- 圆形角色能沿每条路径边通过，导航与碰撞一致，保留道路未被覆盖。
- 对称编辑按组完成；室内外门户方向配对完整。
- 图片没有私增障碍或入口，alpha、锚点、动画帧和素材映射正确。
- 实际游戏中走到树/建筑前后、通过门和狭窄通道，检查遮挡与透明化。
- 桌面和移动视口均检查 UI 遮挡、文字、素材裁切和比例。

测试通过说明的是执行过的这些条件，不代表没有所有 bug。没有 token 消耗对照实验就不写“节省百分之多少”；没有公开地址就不放发布链接。介绍方法与量化收益是两件事。
